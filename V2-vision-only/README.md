# V2-vision-only — ESP32-CAM: เห็นกรวย → หากึ่งกลางเลน (ไม่ขับรถ)

จุดเริ่มต้นใหม่ของโปรเจกต์: ESP32-CAM ถ่าย → ส่งมาที่เครื่อง → แสดงผล → (ถ้าเปิด) หากรวยสีฟ้าในภาพ
สแนปช็อตของ `../V2/` ณ จุดก่อนที่จะเพิ่มระบบควบคุมรถ

สายงาน: `วิดีโอ → cone_detection → lane_center` — จบตรงนั้น
**ไม่มี `autopilot.py`, `robot_link.py`, `autodrive.py` และไม่มีเฟิร์มแวร์หุ่นยนต์**
ที่นี่ไม่มีอะไรส่งคำสั่งไปที่มอเตอร์ได้เลย แม้แต่บรรทัดเดียว ปลอดภัยที่จะรันทิ้งไว้ตอนต่อรถอยู่

ถ้าต้องการให้รถวิ่งจริง ใช้ `../V2/autodrive.py`

## รัน

```
cd V2
python run.py                          # หากล้องเอง
python run.py --esp-ip 192.168.8.191   # รู้ IP แล้ว ข้ามการสแกน
python run.py --source esp32           # ใช้เฟิร์มแวร์หุ่นยนต์ (UDP) แทน
python run.py --framesize qvga         # เล็กลง เร็วขึ้น
python run.py --flip both              # กล้องติดกลับหัว
python run.py --detect                 # เปิดการตรวจจับกรวย + แถบจูน HSV
```

ในหน้าต่างภาพ: กด `v` พลิกบน-ล่าง, `h` พลิกซ้าย-ขวา, `s` เซฟเฟรมลง `./esp32_samples/`, `w` เขียนค่าที่จูน (เฉพาะ `--detect`), `q` ออก
มุมบนซ้ายบอกความละเอียด / fps / สถานะ flip / จำนวนที่เซฟไปแล้ว

### เรื่อง flip

`--flip` มี `none` (ค่าเริ่มต้น) / `v` (บน-ล่าง) / `h` (ซ้าย-ขวา) / `both` (กลับหัว)

ถ้าใช้ `--source webserver` โปรแกรมจะสั่ง **พลิกที่ตัวเซนเซอร์** (`/control?var=vflip` กับ `var=hmirror`)
ดีกว่าพลิกด้วย OpenCV เพราะไม่กิน CPU ฝั่ง PC และภาพในเบราว์เซอร์ก็จะตรงกับที่ Python เห็น
ถ้ากล้องไม่ยอมรับ หรือใช้ `--source esp32` (เฟิร์มแวร์ UDP ไม่มี HTTP endpoint) จะ fallback ไปพลิกด้วย `cv2.flip` แทน — บรรทัดที่ print ตอนเริ่มบอกว่าใช้ทางไหน

ค่าที่พลิกฝังอยู่ในเซนเซอร์จนกว่ากล้องจะ reboot โปรแกรมเลย**สั่งทุกครั้งที่เปิด แม้ตอน `--flip none`** เพื่อเคลียร์ค่าที่ค้างจากรอบก่อน (ไม่งั้นจะงงว่าทำไมภาพกลับหัวทั้งที่ไม่ได้สั่ง)

ค่าเริ่มต้นเป็น **VGA (640×480)** ให้ตรงกับเฟิร์มแวร์หุ่นยนต์ (`sketch_jul13a.ino`)

เครื่องมือแยก ถ้าอยากใช้ทีละชิ้น:

```
python mjpeg_video_source.py --esp-ip 192.168.8.191    # เช็กว่าภาพมาไหม เฉยๆ
python capture_esp32_samples.py --source webserver --esp-ip 192.168.8.191
```

## เรื่องที่มักจะเจอ

- **ต่อได้ทีละคนเดียว** ESP32-CAM รับ stream client ได้แค่ 1 — ถ้าเปิดหน้าเว็บกล้องค้างไว้ในเบราว์เซอร์ Python จะไม่ได้เฟรมเลย ปิดแท็บก่อน
- **การเปลี่ยนความละเอียดไม่ถาวร** `run.py` สั่งผ่าน HTTP ทุกครั้งที่เปิด กล้อง reboot แล้วกลับเป็น QVGA ก็หายเอง ถ้าอยากให้ถาวรแก้ `FRAMESIZE_QVGA` → `FRAMESIZE_VGA` ที่ `CameraWebServer.ino:96` แล้วแฟลชใหม่
- **อย่า hardcode เลข framesize** `val` ใน `/control?var=framesize&val=N` เป็น index ดิบของ enum `framesize_t` และ core esp32 บนเครื่องนี้ (4.0.0-alpha1) แทรก `128X128` กับ `320X320` เข้าไป ทำให้ VGA = 10 ไม่ใช่ 8 ตามที่เว็บส่วนใหญ่บอก — `camera_control.py` เลยลองแล้ววัดผลจริงผ่าน `/capture` แทนที่จะเชื่อเลข
- **ภาพกระตุก = ลูปกินซีพียูจนแย่ง thread ที่รับภาพ** `get_frame()` คืนภาพเดิมซ้ำไปเรื่อยๆ ถ้าลูปประมวลผลทุกรอบโดยไม่เช็กว่าเฟรมใหม่มาหรือยัง
  มันจะรัน detection + `imshow` ~500 ครั้ง/วินาที กับภาพที่มาจริงแค่ ~20 เฟรม/วินาที → ซีพียูเต็มคอร์ → thread ที่รับ UDP ไม่ได้รัน → buffer ล้น → chunk หาย → เฟรมประกอบไม่ครบ → **กระตุก**
  บน TCP (MJPEG) อาการจะออกเป็นดีเลย์แทนที่จะกระตุก เพราะข้อมูลไม่หาย `run.py` เลยเช็ก `src.frame_count` ก่อน ถ้ายังเป็นเฟรมเดิมก็ `cv2.waitKey(5)` แล้วข้ามไป
- **MJPEG บน TCP ดีเลย์มากกว่า UDP ของหุ่นยนต์** ดูภาพเฉยๆ ไม่มีปัญหา แต่ถ้าจะปิด loop กับมอเตอร์เมื่อไหร่ให้ย้ายไป `--source esp32`
- **CameraWebServer ไม่มีระบบควบคุมมอเตอร์** ถ้าจะขับจริงต้องแฟลช `sketch_jul13a.ino` กลับไป

## การตรวจจับกรวยสีฟ้า

```
python run.py --detect                                       # ปกติใช้อันนี้
python cone_detection.py --source webserver --esp-ip <ip>    # ตรวจจับอย่างเดียว
python cone_detection.py --source esp32_samples/xxx.jpg      # จูนกับภาพที่เซฟไว้ ไม่ต้องต่อกล้อง
```

**ทำไมฟ้าไม่ใช่ส้ม** — ส้มอยู่ตรงรอยต่อ H=0/179 ต้องยิง `inRange` สองรอบ ส่วนฟ้าอยู่กลางแผง (H≈100) ยิงรอบเดียวจบ
และของที่ทำให้ตัวตรวจจับสีส้มพังในห้องจริง (สีผิวคน กล่องกระดาษ พื้นไม้ โต๊ะ) อยู่ที่ H 5–25 ทับกรวยส้มพอดี ขณะที่ในห้องแทบไม่มีอะไรฟ้าอิ่มสี

**สีอย่างเดียวไม่พอ** ทุกก้อนต้องผ่านตัวกรอง 4 ชั้นก่อนถึงจะนับเป็นกรวย

| ตัวกรอง | ตัดอะไรออก |
|---|---|
| `min/max_contour_area` | จุดรบกวนจาก JPEG กับผนัง/พื้นทั้งแผ่น |
| `min/max_aspect_ratio` (w/h 0.2–1.3) | กรวยสูงกว่ากว้าง → ตัดยีนส์ พนักเก้าอี้ จอมอนิเตอร์ |
| `min_solidity` (0.75) | ก้อนเว้าแหว่ง (พื้นที่ contour ÷ convex hull) |
| `roi_top_ratio` (0.4) | ทุกอย่างเหนือเส้นขอบฟ้า — ท้องฟ้าผ่านหน้าต่าง จอ เสื้อคน |

ROI ทำโดย**ล้าง mask ส่วนบน ไม่ใช่ crop ภาพ** พิกัดที่ได้จึงเป็นพิกัดเต็มเฟรม ไม่ต้องบวก offset กลับทีหลัง (จุดที่พลาดกันบ่อย)

**ค่าตั้งต้น** H 90–130, S≥80, V≥40 — `S min` 80 เพราะฟ้าซีดเยอะกว่าที่คิด, `V min` 40 เพราะกรวยฟ้าเข้มกว่าส้มโดยธรรมชาติ ตั้ง V สูงแบบส้มจะหลุดหมด

**`min_contour_area` เป็นพิกเซลดิบ** ผูกกับความละเอียดที่กล้องส่งมา 1500 px ≈ 0.5% ของ VGA แต่ ≈ 2% ของ QVGA — เปลี่ยน `--framesize` เมื่อไหร่ต้องจูนใหม่

### ต้องล็อก AWB ก่อนจูนเสมอ

`run.py` ล็อกให้อัตโนมัติแล้ว (ปิดด้วย `--no-lock`) auto white balance ทำงานโดยปรับ gain ของช่อง**น้ำเงิน/แดง** ตรงๆ ซึ่งเป็นแกนเดียวกับที่กรวยฟ้าอยู่ — จูน HSV ตอน AWB ยังวิ่ง = ได้ค่าที่อธิบาย "อารมณ์ของกล้องตอนนั้น" ไม่ใช่สีกรวย พอแสงเปลี่ยนก็ใช้ไม่ได้

กล้องจะค้างค่าที่ auto ปรับไว้ ณ วินาทีที่ล็อก โปรแกรมเลยรอ 2 วิให้นิ่งก่อน — **หันกล้องไปที่สนามจริงตอนนั้น** ไม่งั้นจะล็อกค่าที่ยังปรับไม่เสร็จ (ภาพจะออกเขียวหรือชมพู)

## จุดกึ่งกลางเลน

```python
from cone_detection import ConeDetector
from lane_center import LaneFinder

det = ConeDetector()
lane = LaneFinder(det.cfg)          # ใช้ config ก้อนเดียวกัน

cones, mask, debug = det.detect(frame)
r = lane.update(cones, frame.shape[1], frame.shape[0])

r.target_x      # px — กึ่งกลางช่องว่างอยู่ตรงไหน
r.offset_norm   # -1.0 (ช่องว่างอยู่ซ้ายสุด) .. +1.0 (ขวาสุด), 0 = ตรงกลางพอดี
r.state         # both / left / right / lost
r.have_target   # False = ค่าที่ได้เป็นของเก่าค้างไว้ อย่าเอาไปขับ
```

`offset_norm` คือค่าที่ตัวคุมพวงมาลัยจะกินต่อ — **ในโฟลเดอร์นี้ไม่มีตัวคุม** ไม่มี gain ไม่มีคันเร่ง ไม่มีอะไรที่ทำให้รถขยับ

### 4 เรื่องที่ทำให้มันไม่ใช่แค่ `(ซ้าย + ขวา) / 2`

**1. จะรู้ได้ยังไงว่ากรวยไหน "ซ้าย" ไหน "ขวา"** — แบ่งที่กึ่งกลางเฟรมใช้ได้เฉพาะตอนรถอยู่กลางเลนอยู่แล้ว
คือตอนที่ไม่ต้องการคำตอบ พอรถเบี่ยงมากๆ กรวยทั้งสองอันจะไปอยู่ฝั่งเดียวกัน แล้วโค้ดจะสรุปว่า "มีแต่กรวยซ้าย ไม่มีขวา" → สั่งเลี้ยวผิดทางหนักขึ้นไปอีก
แก้สองชั้น: แบ่งที่**จุดกึ่งกลางเลนที่จำไว้รอบก่อน** (ซึ่งขยับตามรถ) และถ้ายังไปกองฝั่งเดียวอยู่ ให้**แบ่งที่ช่องว่างกว้างสุดระหว่างกรวยเอง** — ซึ่งก็คือช่องที่รถต้องวิ่งผ่านนั่นแหละ ชั้นที่สองคือตัวที่ช่วยเฟรมแรกสุด ตอนที่ยังไม่มีอะไรให้จำ

**2. ห้ามจับคู่กรวยที่อยู่คนละระยะ** — กรวยซ้ายใกล้ๆ จับคู่กับกรวยขวาไกลๆ ได้จุดกึ่งกลางที่เบี้ยว และแกว่งทุกครั้งที่กรวยไกลโผล่หรือหาย → คู่ที่ระยะต่างกันเกิน `max_pair_depth_diff_ratio` จะถูกปฏิเสธ ใช้อันที่ใกล้กว่าอันเดียว
"ระยะ" วัดจาก**ขอบล่างของกล่อง ไม่ใช่จุดศูนย์กลาง** เพราะฐานกรวยอยู่ติดพื้น จุดศูนย์กลางจะเลื่อนเวลากรวยโดนขอบเฟรมตัดด้วย ซึ่งไม่เกี่ยวกับระยะเลย

**3. เห็นข้างเดียวคือเรื่องปกติในโค้ง ไม่ใช่ error** — โค้ดเก่าเดาโดยใช้เศษส่วนของความกว้างเฟรม (`single_side_offset_ratio` ที่คอมเมนต์ในโค้ดเองยังบอกว่าเป็นค่าเดา)
ตัวนี้**จำความกว้างเลนจริงจากตอนที่เห็นครบสองข้าง** แล้วเอามาใช้ → เป็นค่าที่วัดได้ ไม่ใช่ค่าเดา (ค่าเดาใช้เฉพาะก่อนเห็นครบสองข้างครั้งแรก)

**4. ขอบกรวยขยับไปมาทุกเฟรมจาก JPEG noise** → เอาต์พุตผ่าน EMA ตั้ง `target_smoothing = 0` ถ้าอยากได้ค่าดิบ

### ค่าที่ปรับได้ (อยู่ใน `cone_config.json` ก้อนเดียวกัน)

| คีย์ | ความหมาย |
|---|---|
| `lane_half_width_ratio` | ครึ่งความกว้างเลนสำรอง ใช้ก่อนวัดค่าจริงได้ |
| `max_pair_depth_diff_ratio` | คู่กรวยที่ระยะต่างกันเกินนี้ = ไม่จับคู่ |
| `min_lane_gap_ratio` | ช่องว่างต้องกว้างอย่างน้อยเท่านี้ถึงจะนับว่าเป็น "เลน" ไม่ใช่กรวยแถวเดียว |
| `target_smoothing` | 0 = ดิบ, 0.9 = นิ่งมากแต่หน่วง |
| `lane_memory_frames` | หากรวยไม่เจอกี่เฟรมถึงจะทิ้งความจำ |
| `center_deadzone_px` | เบี่ยงน้อยกว่านี้ถือว่าตรงกลางแล้ว กันรถส่ายซ้ายขวา |
