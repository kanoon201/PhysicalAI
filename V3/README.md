# V3 — ESP32-CAM ส่งภาพขึ้นจอ PC

เริ่มใหม่จากศูนย์ เขียนใหม่ทุกไฟล์ ไม่ได้ก๊อปมาจาก `V2/`
**ขอบเขตตอนนี้: ภาพจาก ESP32-CAM มาขึ้นหน้าต่างบน PC เท่านั้น** ยังไม่มีตรวจจับกรวย ไม่มีมอเตอร์

## เฟิร์มแวร์ที่ต้องใช้

`CameraWebServer` (ตัวอย่างมาตรฐานของ Arduino) — MJPEG over HTTP
- พอร์ต 80 = `/status`, `/control`, `/capture`
- พอร์ต 81 = `/stream`

ตั้งบอร์ดเป็น **AI-Thinker ESP32-CAM** และ **เปิด PSRAM** แก้ WiFi SSID/password ที่หัวไฟล์ `.ino` ก่อนแฟลช

## วิธีรัน

ต้อง `cd V3` ก่อนเสมอ (โมดูล import กันเองจาก working directory)

```bash
cd V3
python run.py                                   # สแกนหากล้องในซับเน็ต แล้วโชว์ภาพ
python run.py --esp-ip 192.168.1.42             # รู้ IP แล้ว ข้ามการสแกน
python run.py --framesize qvga --quality 16     # สองปุ่มหลักเวลาภาพช้า
python run.py --esp-ip <ip> --bench 12          # วัดคุณภาพลิงก์ ไม่เปิดหน้าต่าง
python run.py --no-setup                        # ไม่ยุ่งกับเซนเซอร์เลย
```

ปุ่ม: `v` / `h` พลิกภาพ, `s` เซฟเฟรมลง `captures/`, `q` ออก

## ไฟล์

| ไฟล์ | หน้าที่ |
|---|---|
| `camera.py` | หากล้องในซับเน็ต + ตั้งค่าเซนเซอร์ก่อนเปิดสตรีม |
| `mjpeg_source.py` | รับ MJPEG จากพอร์ต 81 คืนเฟรม BGR |
| `run.py` | ตัวรันหลัก: หา → ตั้งค่า → โชว์ |

ต่อโค้ดใหม่ผ่าน `src.get_frame()` ที่คืน **BGR** จาก `cv2.imdecode` ตรงๆ

## สิ่งที่โค้ดนี้ระวังไว้แล้ว (อย่าแก้ให้หาย)

- **ตั้งความละเอียดก่อนเปิดสตรีม** กล้องรับ client สตรีมได้ตัวเดียว ถ้าสตรีมค้างอยู่ `/capture` ที่ใช้ยืนยันผลจะรันไม่ได้
  และ CameraWebServer บูตมาที่ QVGA เสมอ ถ้าไม่สั่งจะได้ภาพนุ่มๆ 320×240
- **ไม่ hardcode เลข framesize** `val` ใน `/control?var=framesize&val=N` เป็น index ดิบของ enum ซึ่งเลื่อนตามเวอร์ชัน esp32 core
  `camera._probe_framesize()` เลยไล่ลองแล้วยืนยันด้วย `/capture` จริง
- **ล็อก AWB/AEC/AGC หลังปล่อยให้ภาพนิ่ง 2 วิ** และต้องเขียน `ae_level` **ก่อน** ล็อก AEC ไม่งั้นค่าถูกแช่ทิ้งไปเฉยๆ
  (`ae_level -1` กันไม่ให้ AEC เลือก exposure ยาวกว่าคาบเฟรมจนเฟรมเรตของเซนเซอร์เองพัง)
- **อ่านซ็อกเก็ต MJPEG ด้วย `read1()` ห้ามใช้ `read()`** `read()` จะบล็อกจนครบ n ไบต์ ทำให้ JPEG ที่เสร็จแล้วนอนรอจนเฟรมถัดไปเริ่มมา = ดีเลย์หนึ่งเฟรมเป๊ะๆ ภาพจะมาเป็นคู่ๆ เหมือนกระตุก
- **เช็ค `frame_count` ก่อนประมวลผลเสมอ** `get_frame()` คืนภาพเดิมตลอดไป ถ้าลูปทำงานทุกรอบมันจะกินซีพียูเต็มคอร์
  แล้วแย่ง GIL จากเธรดรับภาพ และอะไรก็ตามที่เช็คว่า "มีเฟรมไหม" จะเป็นจริงตลอดกาล
- **`handle_key` ตัวเดียว เรียกจากทั้งสองทางของลูป** `waitKey` กินคีย์ตรงจุดที่ถูกเรียก และทางที่ไม่มีเฟรมใหม่วนถี่กว่ามาก
  ถ้าดักคีย์แค่ตอนมีเฟรมใหม่ จะกดติดไม่ถึง 5%

## เวลาภาพช้าหรือกระตุก

fps เฉลี่ยปิดบังอาการกระตุก — สตรีมที่ส่งมาเป็นคู่แล้วเงียบยาว เฉลี่ยได้เท่าสตรีมที่มาสม่ำเสมอ ใช้ `--bench` ดูระยะห่างระหว่างเฟรมแทน

| อาการ | แปลว่า | แก้ที่ |
|---|---|---|
| ช้า แต่ไบต์เยอะ | แบนด์วิดท์ตัน | `--quality 16-18`, `--framesize` เล็กลง |
| ช้า ไบต์น้อย ระยะห่าง **สม่ำเสมอ** | กล้องผลิตเฟรมไม่ทัน | `--ae-level -1` ก่อน แล้วค่อย `--quality`, ลอง `--no-lock` |
| ช้า ไบต์น้อย มี **ช่องว่างยาวๆ** | ลิงก์วิทยุ | ดู `ping` ทีละบรรทัด, jumper เสาอากาศ, ระยะทาง |

บีบภาพแรงขึ้นไม่ช่วยสองเคสล่าง เพราะเฟรมไม่ได้ใหญ่เกินอยู่แล้ว

- **`ping` บน Windows โกหกในบรรทัดสรุป** ถ้าปลายทางหาย เครื่องเราเองจะตอบ `Destination host unreachable` แล้วนับเป็น "ได้รับ, loss 0%" ให้อ่านทีละบรรทัด ลิงก์ WiFi ที่ดีอยู่ที่ 2–10 ms
- **บอร์ด AI-Thinker เลือกเสา PCB หรือ u.FL ด้วย solder jumper** ถ้าตั้งไว้ที่ u.FL แล้วไม่ได้เสียบเสา บอร์ดยังต่อ WiFi ติดปกติ แต่ throughput พัง
- **เปิดหน้าเว็บกล้องค้างไว้ในเบราว์เซอร์ = Python ไม่ได้เฟรมเลย** เพราะสตรีมรับได้ client เดียว (แต่ `/status` ยังตอบ เพราะคนละ httpd)

## การทดสอบ

ไม่มี test runner — ใช้สคริปต์ใช้แล้วทิ้ง และตั้งใจให้เป็นแบบนี้
- **ตัวรับภาพ**: เปิด HTTP server ในเครื่องที่พูด multipart MJPEG จริง ชี้ `MjpegSource` ไปที่ localhost แล้ววัดจำนวนเฟรม/ดีเลย์/ลำดับช่อง BGR
- **`camera.py`**: เซิร์ฟเวอร์จำลองที่ตอบ `/status` `/control` `/capture` โดยให้ index ที่ "ถูก" ไม่ตรงกับที่คนมักจำ เพื่อพิสูจน์ว่า probe ทำงานจริง
- **ลูปหลัก**: monkeypatch `cv2.waitKey` / `cv2.imshow` แล้วป้อน source ปลอมที่ผลิตเฟรมตามอัตราที่กำหนด — วิธีนี้คือวิธีที่จับบั๊กคีย์หลุดกับบั๊กเฟรมเรตได้
